# M6.4 结果记录：五项体验改进

依据 `docs/M6.4_ux_research.md`，按请求顺序实施。本文件记录实现要点、AI 测量条件与结果，以及验证方式。所有截图和测量均由脚本驱动，**未做真人试玩**。

## 1. 己方上一炮

- `battle.py`：每枚炮弹多了只读标记 `center`。普通炮弹、齐射中间那枚（偏移 (0, 0)）、空爆分裂后水平速度系数为 1 的那枚为 `True`，未分裂的母弹也是 `True`。落点事件（`explosion` / `miss`）带上这个标记。规则代码从不读取它。
- `main.py`：新增小类 `ShotRecord`，记录开火时炮台的角度、火力（即中心弹的瞄准）和每枚炮弹的落点事件。最后一枚落地后，记录才成为该队的“上一炮”。
  - 轮到该队、且由真人瞄准时，面板左组最后一行用金色显示，例如 `Last shot · 45° / 83 · DIRECT HIT`。多弹显示合计，例如 `2 direct, 1 ground`。
  - 战场上用半透明空心圈标出中心弹落点，旁边写 `last`。
  - 中心弹侧边出界时只显示文字；没有可识别的中心弹时也只显示文字（合计）。
  - 重赛和换队时清空。记录只读，不会替玩家调整瞄准。

## 2. 高抛追踪

至少一枚炮弹在窗口上沿之上（`y < 0`）时，HUD 下方（y = 80）出现金色向上三角和文字 `Shell above view`；多枚时显示 `3 shells above`，三角位于这些炮弹横坐标的平均处，靠边时向内收，保证文字不出窗口。炮弹回到画面内或落地后，标记立即消失。

侧边出界的炮弹会被战斗规则当场判为 miss，从飞行列表中移除，所以不会被画成“仍在飞”。

用真实引擎复现：

| 发射 | 在画面上方的帧数 | 首帧 / 末帧横坐标 |
|---|---:|---|
| 左炮 75° / 100 | 39 | 587.6 / 702.3 |
| 左炮 80° / 100 | 57 | 491.9 / 605.4 |
| 右炮 75° / 100 | 39 | 692.4 / 577.7（= 1280 − 左炮） |
| 右炮 80° / 100 | 57 | 788.1 / 674.6（= 1280 − 左炮） |

与调研文档的 39 / 57 帧一致。Gunner 在 75° / 100 发射齐射时，81° 和 75° 两枚飞出上沿，69° 那枚留在画面内，标记显示 `2 shells above`。Bombardier 在 80° / 100 发射空爆时，分裂发生在画面上方，标记从 `Shell above view` 变为 `5 shells above`。

## 3. 防止误按 R

- 对局进行中按 R：比赛暂停，弹出 `Restart match?` / `Current progress will be lost.`，默认按钮为 Continue（金色）。
- 暂停期间 `Game.update()` 直接返回：炮弹、跑动动画、Reflex 摆动、AI 等待、爆炸与飘字全部冻结。
- Continue（Enter、Space、Esc 或点击）从同一帧继续。测试用两局完全相同的输入对照：一局在跑动中暂停 45 帧，另一局不暂停；继续后之后 140 帧的状态逐帧相同。
- Restart 需要一次新的按键（再按一次 R），或点击 Restart 按钮。R 现在和开火键一样“按一次只算一次”：按住 R 只会打开一次询问，不会确认；重开后继续按住也不会再次询问。
- 结算画面上 R 仍然一键重赛。
- 暂停期间只有询问的两个按钮和 M（声音）有效，Esc 表示 Continue，而不是退出。

## 4. AI 思考时的窗口响应

### 测量条件

- 机器：本地开发机（Windows 11），项目 `.venv`（Python 3.11.9、pygame 2.6.1），SDL dummy 视频驱动。
- 阵容：右队（被测 AI）Gunner、Bombardier、Medic；左队 Knight、Archer、Engineer。双方 AI 各自布防（`choose_layout`）。
- 决策耗时：`time.perf_counter()` 计时 `AIController.choose()`。“首回合”为右队先手，每档难度 4 个种子；“整局”为每档难度 2 局完整的 AI 对 AI 对局中右队的全部决策。
- 窗口帧时间：与 `main.main()` 相同的一帧（处理事件、`update()`、`draw()`、`flip()`），不含 `clock.tick` 的等待。左队由脚本控制，能防御就防御，否则开火；每档难度 3 个种子 × 6 个电脑回合。每帧开始前投递一个 M 键事件：电脑做决定的那一帧有多长，按键就要等多久。

### 改动前

| | Easy | Normal | Hard |
|---|---:|---:|---:|
| 首回合决策：中位 / 最长 | 143 / 268 ms | 146 / 298 ms | 278 / 283 ms |
| 整局决策：中位 / 最长 | 114 / 285 ms | 132 / 303 ms | 150 / 275 ms |
| 同一决策内的重复模拟 | 1.5% | 4.7–5.5% | 9.7–13.8% |
| 40 帧等待中每帧耗时：中位 / 最长 | 1.5 / 4.9 ms | 1.7 / 5.4 ms | 1.8 / 6.2 ms |
| 决策那一帧：中位 / 最长 | 175 / 297 ms | 182 / 355 ms | 379 / 458 ms |

可见 40 帧的展示等待本身很轻（每帧约 2 ms），卡顿全部来自第 40 帧里同步完成的决策计算：最长约 0.46 秒，这期间窗口不处理任何输入（关闭、静音都要等这一帧结束）。

调研文档写的中位数约 522 / 602 / 642 ms，与本机测得的 143 / 146 / 278 ms 不同，可能是机器或测量方式不同；本文件只用本机数据比较改动前后。

### 原型对照（同一批 45 个决策，固定种子）

| 方案 | Hard 决策帧：中位 / 最长 | 与原方案相同的决策 |
|---|---:|---:|
| 原方案 | 289 / 400 ms | — |
| 只去掉重复模拟 | 241 / 312 ms | 45 / 45 |
| 去重 + 扫描在等待中算好 | 97 / 166 ms | 45 / 45 |
| 去重 + 扫描和所有候选都在等待中算好 | 27 / 35 ms | 45 / 45 |

只去重的改善约 16%，仍有明显卡顿。由于 40 帧等待里每帧还有约 14 ms 空闲，足够容纳整个决策，所以采用了分帧计算。

### 实现

- `AIController.imagine()`：在一次决策内记住每次模拟的结果。键为（角色位、动作、截到合法范围后的角度和火力）。规则里没有随机数，同一枪模拟两次结果完全相同，所以记忆只省时间、不改结果。只在同一个 `Battle` 对象上复用；决策结束、重赛时清空。
- `AIController.thinking_ahead()`：一个生成器，每一步模拟一枪：先是扫描（攻击计划一定会做的那部分），然后是攻击计划可能评估的所有候选（可选目标的瞄准 × 存活射手 × 普攻与开火特技 × 火力误差两端），最后是 Repair。它不掷骰子、不改分数。
- `main.py`：电脑回合的每一帧最多花 10 ms 推进这个生成器（`AI_THINK_SECONDS`），第 40 帧照旧调用 `choose()`。若慢机器还没想完，`choose()` 会自己补算剩下的部分，结果相同，只是那一帧较长。
- 难度设置、打分、随机顺序、合法行动的检查都没有改。

### 改动后（同一脚本、同一种子）

| | Easy | Normal | Hard |
|---|---:|---:|---:|
| 决策那一帧：中位 / 最长 | **30 / 43 ms**（原 175 / 297） | **37 / 42 ms**（原 182 / 355） | **36 / 41 ms**（原 379 / 458） |
| 40 帧等待中每帧：中位 / 最长 | 12.5 / 44.2 ms | 12.6 / 46.6 ms | 12.3 / 61.5 ms |
| 每回合帧数（决定出现在第几帧） | 40 | 40 | 40 |
| 同一决策内的重复模拟 | 0 | 0 | 0 |
| 只有去重、不提前思考时 `choose()`：整局中位 / 最长 | 152 / 383 ms | 172 / 337 ms | 178 / 293 ms |

- 按键等待（=最长的一帧）从最长约 458 ms 降到最长约 62 ms。电脑仍在第 40 帧做出决定，所以回合节奏不变。
- 等待帧的中位数变成约 12.5 ms：每帧最多 10 ms 思考，加上约 2 ms 绘制，仍在 1/60 秒（16.7 ms）之内。
- 剩下的两处较长帧来自同一件事：扫描结束后的“追踪路线 + 给目标排序”是不可再分的一步，耗时 26–34 ms（其余每一步最长 7.9 ms，中位 1.5 ms）。它在等待中做一次，`choose()` 在第 40 帧又做一次。若要进一步消除，可以把这一步的结果也记住，或者把路线追踪也拆成逐步的生成器；本轮为保持实现简单，没有继续拆。
- “只有去重”一行比上午的改动前数据（114–150 ms）还高，原因是两次测量时机器负载不同。为排除这一点，又在同一进程里交替计时同一批 58 个决策（每个跑两遍）：不去重 Easy / Normal / Hard 中位 188 / 194 / 314 ms、最长 396 / 461 / 427 ms；去重 186 / 189 / 264 ms、最长 375 / 383 / 328 ms。去重本身有效但幅度小（与 1.5–14% 的重复比例相符），真正消除卡顿的是把计算挪进等待帧。

### 固定种子对照

用改动前保存的决策记录（同一脚本、同一种子）与改动后逐个比较：首回合 12 / 12、整局 102 / 102 个决策完全相同（角色、动作、目标、角度、火力）；重复模拟从 432 次降为 0。另有测试锁定：对 6 组种子 × 4 个决策，提前思考与不提前思考得到同一计划，随机数状态也相同；提前思考完成后，`choose()` 不再新模拟任何一枪。

## 5. 快速试炮场

- 选队页 PLACE COVER 旁边新增 `Practice`，不选队也能进入。
- 左队固定为 Archer、Gunner、Bombardier（1–3 选择），右队靶子为 Knight、Archer、Engineer，双方默认掩体，没有电脑。
- 射击使用正式对局的同一套战场、跑动、炮弹、伤害代码。测试对照：同一发空爆在试炮场和普通 `Battle` 中造成完全相同的伤害。
- 每发结算后（回合交给右队的那一帧），`Battle.reset()` 恢复靶子、掩体和技能冷却，左队再次行动；保留炮台角度、火力和“上一炮”记录。单发最大伤害 60（Power Shot），最弱靶子有 90 HP，所以试炮永远不会结束对局。
- 面板右组改为 Classic / Reflex / Back 三个按钮；Backspace = Back，R = 立即重置。按键沿用选队页所选模式（人机：方向键 + Space；双人：左队 W/S、D/A、F）。DEFEND 在试炮场中置灰，注明 `shots only`。
- Back 回到选队页，模式、难度、人数、选人、瞄准方式、掩体都保持进入前的样子。试炮场里切换的 Classic / Reflex 不影响选队页的设置。
