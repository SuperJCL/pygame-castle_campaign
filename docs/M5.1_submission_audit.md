## 1. Instructor requirements (confirmed by the Project Manager)

The Project Manager read both original instructor PDFs, "CS5001 Final Project Games based
Project" and "CS5001 final project rubrics updated", and confirmed the findings below. They
replace the provisional M5.1 classification. **The developer (Claude Code) has still not seen
the PDFs themselves**, so the wording below is the PM's summary, not a quotation.

- **The game:** a Python and Pygame turn-based battle game.
- **Characters and actions:** character selection, HP, Attack, Defend, Special.
- **Interface:** an AI opponent, health bars, buttons, a combat log.
- **Victory:** by eliminating the enemy units.
- **Presentation:** a background, and sounds for attack, defence, victory and defeat.
- **Source code:** the complete Python source code must be submitted, and the updated rubric
  asks for it to be copied into the final report.
- **Screenshots:** of gameplay, testing and final results.
- **Explanation:** 300–500 words on how the code works, especially the game loop, turn handling
  and the GUI.
- **Demo video:** not a mandatory deliverable.
- **Numbers:** the damage and EXP examples allow student-defined values.

## 3. The explanation (report §2)

- **Word count: 435**, counted by script as whitespace-separated words between the
  `<!-- explanation:start -->` and `<!-- explanation:end -->` markers. A stricter count that
  splits names such as `pygame.event.get()` gives 455. Either way it is within 300–500.
- **It covers what the instructor asks for:**
  - the main loop: `pygame.event.get()`, `Game.handle_event()`, `Game.update()`, `Game.draw()`
    and `pygame.display.flip()`;
  - how an action resolves: `Battle.perform_action()`, `why_not_allowed()`, the run to the
    cannon, `Battle.update()` moving the projectile, collision along the path, the explosion and
    damage;
  - how the turn changes: EXP, the elimination check, the round limit, the next team,
    cooldowns, and the computer's turn;
  - how the GUI responds to Battle events: `take_events()`, combat log, effects, sounds, the
    result screen, and buttons enabled from `why_not_allowed()`.
- **It contains no code listing** and claims nothing that isn't built.

## 4. Source code in the report (Appendix B)

- **How it was made:** a script reads each file with `git show a4ceef8:<file>` and writes it
  into the report in a fenced Python block. The eight files go in a fixed order: `main.py`,
  `battle.py`, `characters.py`, `castle.py`, `ai.py`, `animation.py`, `drawing.py`,
  `sound.py`. Each has a heading with its line count, and a table lists every file's line count
  and SHA-256. Total: **3,620 lines**.
- **How it was checked:** a second script extracts each block from the report and compares it
  with `git show a4ceef8:<file>` and with `git show HEAD:<file>`.
  - **Checked:** the same eight names in the same order, identical bytes, matching line counts
    and matching SHA-256 values, and no other game `.py` file in the repository. **Result:
    verified.**
  - **Shown to fail when it should:** checked against the previous commit `cf72fd1`, it reports
    `main.py` and `sound.py` as different.
- **If the code changes again,** regenerate the appendix from the new commit and re-run the
  check. Code commit `a4ceef8` is the last code change; the later commits change documents only.
- **Tests:** the 8 test files (5,181 lines) are not printed in the report. They are submitted
  with the code. The brief asked for the eight game files. *If the instructor wants the tests in
  the report too, an Appendix C can be generated and verified the same way (a PM decision).*

## 9. The PDF (M5.2-B)

- **File:** `docs/Castle_Siege_Final_Report.pdf`, **82 pages**, 3.4 MB, US Letter. The PDF's
  title is "Castle Siege — CS5001 Final Project Report".
- **How it was made:** headless Chrome printed `docs/M5_final_report.md`. A throwaway script
  converted the Markdown in the page with the `marked` library (loaded from a CDN) and added
  print styles. Chrome's own printer made the PDF. Nothing was installed and no project
  dependency was added. The report's text is not changed by the export.
- **Layout:**
  - title page and contents (page 1);
  - the explanation (page 2), gameplay, algorithms, the OOP section with Figure 1, testing with
    Figure 2;
  - two screenshots per page (pages 11–16), final results, the AI disclosure and references
    (page 17);
  - Appendix A (pages 18–23): the overview, then one part per page;
  - Appendix B (pages 24–82): the file table, then each file starting on a new page.
- **Code:** Consolas 8 pt with line numbers in a separate gutter; indentation kept. The few lines
  longer than the page (the longest is 123 characters) continue on the next printed row,
  indented. No code line is split across two pages.
- **Diagrams:** the complete diagram is too large to read at page size, so Appendix A shows it
  as an overview (zoom in to read it) plus five parts, each on its own page.
  - The parts are cut automatically from `docs/M5_class_diagram.mmd`; their sources are
    `docs/M5_class_diagram_part_2.mmd` to `_part_6.mmd`.
  - Together they cover all 20 classes and all 23 relationships, each relationship once.
  - Printed text size is about 6.3 pt in Figure 1 and about 6.8–8 pt in the parts. The images
    are high resolution, so they stay sharp when zoomed.
- **Checks on the PDF itself:**
  - **Automatic, before printing:** the page confirmed that all 20 images loaded, all 20 figures
    have a caption, and all 3,620 code lines are present.
  - **By eye:** I drew the printed PDF with pdf.js in a browser (the Read tool can't render PDFs
    here). I looked at every page as thumbnails, and at full size at pages 2, 7, 10, 11, 17, 20,
    24, 25, 50 and 82: the beginning, the diagrams, the screenshots, the start of the code,
    the middle of the code and the last page.
  - **Defects found and fixed:** diagrams cut across pages, nearly empty pages, and one
    screenshot per page.
  - **Privacy:** no local path or user name appears anywhere in the PDF bytes, including the
    compressed streams.
- **Re-exporting** after the student fills in the placeholders: the export script is a
  throwaway, not part of the project. The developer re-runs it on request.
