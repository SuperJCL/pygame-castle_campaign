## 4. Submission-completeness plan: the complete Python source code

If the instructor expects the complete source code **inside the report**:

1. **Freeze the commit.** The submitted code is one commit; its SHA goes on the report's first
   page. Run `python -m unittest discover tests` on exactly that commit.
2. **Generate the appendix by script, not by copy and paste.** In M5.2, a small script reads
   each file with `git show <sha>:<file>`. For each one it writes a heading (file name, line
   count, one-line purpose) and the code in a monospace block with line numbers, so the appendix
   always matches the commit.
   - **Order:** `main.py`, `battle.py`, `characters.py`, `castle.py`, `ai.py`, `animation.py`,
     `drawing.py`, `sound.py`.
   - **Size:** 3,596 lines, about 60–75 pages at 50–60 lines per page in a 9–10 pt font.
3. **Tests:** the 8 test files (5,117 lines, about 90–100 more pages) go in a second appendix
   only if the instructor asks for all code. Otherwise the report lists them with their test
   counts and they are submitted as files.
4. **Check the appendix** against `git ls-files "*.py"` at that commit: no file missing, no
   extra file, same line counts.
5. **Keep the short parts short.** Part A (300–500 words) contains no code. Report §5 and §6
   show only a few short excerpts and refer to the appendix by file and function name.

If code inside the report is **not** required: submit the `.py` files (or a zip of the
repository at that commit, without `__pycache__`), and the report lists the files, their line
counts and the commit SHA.

**In both cases:**
- `requirements.txt` (`pygame==2.6.1`) and the README's run instructions are part of the
  submission.
- A fresh-clone test should be done before submitting: `pip install -r requirements.txt`,
  `python main.py`, then the tests.
- The PDF / Word conversion method is chosen in M5.2. No new project dependency is needed.

## 6. Instructor compliance risks (highest first)

1. **The instructor's documents were not checked** (§1). Every "mandatory" or "example" label
   is our reading; a requirement we never recorded could be missing.
2. **Custom rules without instructor approval:**
   - cover placement;
   - Cover Guard;
   - Guarded Strike;
   - the anti-stall rule;
   - the round-30 draw;
   - artillery shots that can miss (C3);
   - one shared cannon per team (C6).
   They are documented as ours and can each be switched off or changed in one place, but
   gameplay is frozen.
3. **Damage formula:** deterministic ATK − DEF instead of the sample's random −5 to +10 (R11).
   This is a risk only if the instructor requires the sample formula, not just shows it.
4. **Interpretations:**
   - the AI defends with a probability, not always, below 50 % HP (C4);
   - "turn-based" is per team, not per character (C1);
   - Defend halves damage after DEF (C5).
5. **Missing submission parts:**
   - the final PDF / Word report;
   - an exported class-diagram image;
   - the demo video (if required);
   - the source-code appendix (if required);
   - the AI-assistance statement.
6. **Academic integrity:** the project was planned with ChatGPT and implemented with Claude
   Code. The course's policy on AI tools, and what must be disclosed, is unknown; the report
   has a placeholder for the student's statement. The Rebound reference is cited as ideas only
   (Q4 still open).
7. **No human play-test of the final version.** Two M4.2-A audio items are unverified (§7).
8. **Screenshots:** Fig. 7 is staged, and all eight come from scripted runs (§5).
9. **Clean code:** `main.py` is 1,415 lines; no style checker has been run (none is installed,
   and new tools are out of scope).
10. **The graders' environment is unknown** (Python version, operating system; Q2). Tested only
